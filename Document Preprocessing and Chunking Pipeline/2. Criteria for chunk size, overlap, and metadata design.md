# Criteria for chunk size, overlap, and metadata design  
After extracting text from documents, it must be split into smaller units called ***chunks***. Since *RAG retrieves chunks rather than entire documents, chunking plays a key role* in retrieval quality.​‌  
Let's check why chunking is necessary, different chunking strategies (fixed-size and semantic chunking), how overlap preserves context across chunk boundaries, and how metadata can be used to improve retrieval quality.  

## Necessity of chunking  
Why do we need chunking? There are two main reasons:  
- **Input length limits**: Embedding models and LLMs can process only a limited number of tokens at a time, so large documents must be split into smaller chunks.  
- **Retrieval accuracy**: Representing an entire document as a single vector can dilute its topics. Retrieving a focused chunk containing the relevant information typically produces more accurate results.  

However, chunks that are too small may lose context and scatter related information across multiple chunks. The goal is to find a balance: chunks should be large enough to answer a question, yet small enough to remain topically focused.  

## Fixed-size chunking vs semantic chunking: a practical comparison  

### Fixed-size chunking  
Fixed-size chunking splits text into chunks of a *predefined size*. 'RecursiveCharacterTextSplitter' in LangChaing is a common example, where chunk_size is based on characters by default.  

### Sematic chunking  
Semantic chunking creates chunks *based on meaning*, grouping related content together. It is also supported by Amazon Bedrock Knowledge Bases.  

The figure below compares two ways of splitting the same nine sentences. Semantic chunking cuts where **embedding similarity between adjacent sentences falls below a threshold** (a topic shift). Fixed-size chunking cuts at **set lengths regardless of content**, so misaligned boundaries mix two topics in one chunk.

| Criteria | Fixed-Size Chunking | Semantic Chunking |
| :--- | :--- | :--- |
| Splitting basis | Character/token count | Changes in semantic similarity |
| Chunk size | Uniform | Variable (depends on content) |
| Implementation difficulty | Easy | Moderate (requires an embedding model) |
| Cost | Low | High (requires embedding API calls) |
| Quality | Fair | High (preserves semantic units) |
| Best for | Large document volumes, fast processing | Cases requiring high-quality retrieval |  

## Chunk overlap strategy  
Cutting documents *mechanically* at fixed lengths causes problems. What if a key sentence falls on a boundary? Its meaning splits in two, and it won't be retrieved. **Overlap prevents this:** each chunk begins with the last 10–20% of the previous one, like a sliding window that advances with slight overlap.  

The figure shows a 3000 character document split into 1,000-character chunks with a 200 character overlap. Each new chunk **repeats the previous one's last 200 characters, easing context breaks**. Sentences shorter than the overlap can fit whole in one chunk, but preservation depends on sentence length and split position. The last chunk may be shorter. Ideal overlap is 10–20% of chunk size: 50–100 characters for 500-character chunks.

Note: overlap adds chunks and storage but *reduces retrieval failures from broken context*. Knowledge Bases for Bedrock(Amazon) lets you set an overlap percentage for fixed-size chunking.  


## Metadata design  
**Every chunk must carry a "tag": metadata**. It lets the LLM *cite sources*, such as "Based on page 15 of the HR policy."
Recommended metadata fields are as follows:  
| Field | Example | Purpose |
| :--- | :--- | :--- |
| `source` | `"2025_HR_Guide.pdf"` | Track the source file |
| `page` | `15` | Page number |
| `category` | `"HR Policy"` | Document classification (for filtering) |
| `created_date` | `"2025-03-01"` | Assess document recency |
| `department` | `"HR Team"` | Filter by department |  

In Knowledge Bases for Bedrock, `.metadata.json` files stored with documents in S3 link metadata automatically, enabling search filtering by category or date range.  

### Validation checklist:  
- Have you printed a few resulting chunks to check that not many are cut off mid-sentence?
- Have you distinguished whether chunk length is measured in characters (LangChain) or tokens (Knowledge Bases)?
- Do all chunks retain `source` and `page`?
